## 1. 點子比較與選定

| # | 點子 | 給誰第二次機會 | 主要風險 |
|---|---|---|---|
| A | **冰箱第二春**：宿舍冰箱裡快過期的食材 → 推薦「只用電鍋／微波爐」就能做的救援料理，煮完記一筆「救回了多少」 | 快被丟掉的食材 | 「剩食」題材常見，要靠宿舍限定角度做出差異 |
| B | **計畫復活所**：把半途而廢的計畫丟進來，AI 拆成 15 分鐘小步驟並陪你打卡 | 被放棄的計畫 | 核心靠 AI，但部署沙箱沒網路；離線備案很弱，示範較抽象 |
| C | **校園物品接力站**：用不到的課本、宿舍用品刊登，讓學弟妹認領 | 用不到的物品 | 類似服務很多；示範要兩個人才演得出來 |

依評分比重打分（1–5 分）：

| 評分項目（比重） | A 冰箱第二春 | B 計畫復活所 | C 物品接力站 |
|---|---|---|---|
| 主題符合度（30%） | 5 | 4 | 4 |
| 創意與主題契合（24.5%） | 3.5 | 4 | 2 |
| 技術實作可完成度（24.5%） | 5 | 3 | 4 |
| 展示與表達（21%） | 5 | 3 | 3 |
| **加權總分** | **4.63** | 3.55 | 3.30 |

**選定 A：冰箱第二春。** 理由：
1. 「快過期食材 → 變成一餐」是最直觀的第二次機會，30% 的主題分最穩。
2. 核心推薦用**規則式比對**（不靠外部 AI）就能完整運作，部署沙箱沒網路也不怕；AI 只是加分。
3. 和比賽名稱「吃客松」呼應，攤位示範 3 分鐘內就能從「看到快過期」走到「救回一餐」。
4. 創意差異點：**宿舍限定**——食譜只用電鍋／微波爐、可標記食材屬於哪位室友，貼近大學生真實處境。

## 2. 目標使用者

- **主要**：住宿舍、共用冰箱的大學生（沒有瓦斯爐，只有電鍋、微波爐）。
- **痛點**：買了食材忘記吃、室友的東西放到壞、不知道剩下那幾樣能煮什麼。

## 3. 一句話介紹

> 「打開冰箱第二春，勾選快過期的食材，30 秒找到只用電鍋就能做的救援料理。」

## 4. 核心流程（攤位示範就走這條）

1. **首頁「我的冰箱」**：一打開就看到種子資料的食材清單，依到期日排序，用顏色標示（紅：今天/明天到期、黃：3 天內、綠：其他）。上方顯示「已救回 N 樣、省下 NT$X」。
2. **勾選食材**：勾 1–3 個快過期食材，按「給它們第二次機會」。
3. **推薦食譜**：列出 3–5 道電鍋／微波爐料理，每道顯示「用到你選的：雞蛋、白飯」「還缺：蔥（可省略）」、所需時間、器具。
4. **食譜詳情**：看步驟，按「我煮了！」。
5. **救援成功**：顯示成功畫面（動畫或大字），被用掉的食材從清單消失，上方統計數字更新。

另一條次要流程：**新增食材**（名稱、數量、到期日、屬於哪位室友），用來展示「真的可以用」。

## 5. 功能清單

### 必做（第 12 小時前要能從頭跑到尾）
- [ ] 食材清單：依到期日排序、剩餘天數、顏色標示
- [ ] 新增食材、刪除／標記丟掉
- [ ] 勾選食材 → 規則式食譜推薦（優先用掉快過期的）
- [ ] 食譜詳情（步驟、器具、時間）
- [ ] 「我煮了」→ 食材標記為已救援，統計更新
- [ ] 救援統計：已救回幾樣、省下多少錢、丟掉幾樣
- [ ] 種子資料：約 15 樣食材（到期日相對「今天」產生）、約 15 道宿舍食譜
- [ ] 手機寬度（375px）正常顯示
- [ ] **前端離線備案**：API 連不到時，自動改用內建示範資料與前端版規則式推薦，存在 localStorage（瀏覽器內建的小型儲存空間）。原因：「網站預覽網址」只跑網頁、不跑 Python，沒有這個備案就整個不能用。

### 有時間再做（依序）
1. 「分享給室友」：把食材標成「誰要就拿去」，出現在共享區
2. 線上 AI 推薦：有金鑰且有網路時用 AI 產生食譜，失敗自動退回規則式
3. 救援成就徽章（例如「連續 3 天零浪費」）
4. 救援成功音效（對應 Make Some Noise 的小彩蛋，非主軸）

### 不做
- 帳號登入、密碼（省時間、也避免個資問題；室友只是文字標籤）
- 拍照辨識食材（需要外部 AI，沙箱跑不了）

## 6. 技術架構

```
瀏覽器（React + Vite 建置後的靜態檔，UI 用 Astryx）
        │  fetch("/api/...")（相對路徑，不寫 localhost）
        ▼
Python Flask（app.py）── 同一個服務也負責送出根目錄 dist/ 的前端檔
        │
        ├─ SQLite（data/fridge.db，啟動時若空就自動放種子資料）
        └─ 推薦引擎：規則式（必做）／AI（選做，失敗退回規則式）
```

### 平台會產生兩個網址（Sean 確認的平台行為）

| | 網站預覽（上傳後自動） | 部署網址（按「部署」後） |
|---|---|---|
| 平台找什麼 | 只找 `index.html`（根目錄、`dist/`、`build/`） | 平台 AI 分析專案、產生部署計畫 |
| 跑什麼 | 只有網頁，Python 不會執行 | Python 後端（同時送出前端網頁） |
| 我們的作品 | API 連不到 → 前端自動改用內建示範資料 | 完整作品：前端 + 真正的 API + SQLite |

- **部署類型**：Python（python312），一個服務同時提供 `/api/*` 和前端頁面，不用處理跨網域（CORS）。
- **前端**：React 19 + Vite + **Astryx**（Meta 的 React 設計系統，Beta 版），`base: './'`，建置輸出到**專案根目錄的 `dist/`**（Vite 設定 `build.outDir: '../dist'`），讓網站預覽找得到 `index.html`。**dist 要一起放進 zip**。
- **後端**：Flask + gunicorn，讀環境變數 `PORT`、監聽 `0.0.0.0:$PORT`；套件全部列在 `requirements.txt`；金鑰只從環境變數讀。`app.py` 放在專案根目錄，部署的工作目錄就是根目錄。
- **部署計畫檢查**（部署前必看，不對就手動改再部署）：執行環境 `python312`、工作目錄 = 專案根目錄、安裝指令 `pip install -r requirements.txt`、啟動指令 `gunicorn -b 0.0.0.0:$PORT app:app`。
- **沒有對外網路**：部署沙箱連不到任何外部 API；核心功能全部不靠外部服務。

## 7. 已確認事項

- 平台不會只當成一種類型：網站預覽只跑網頁，按「部署」後才跑 Python。兩個網址都要能示範（見第 6 節表格）。
- 啟動指令寫在平台產生的部署計畫裡，可以手動修改。部署前由後端管理員檢查、PM 複核。
